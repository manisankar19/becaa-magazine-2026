# Deployment, rollback and operations — registration application (Sprint v3)

This document covers the server side added in Sprint v3 (visitor registration gate, PostgreSQL, administrator dashboard). It contains **no credentials and no real URLs**; every secret is generated by you and lives only in Vercel's environment variables. Production deployment is a separate approval step (INSTRUCTION.md §18) and is **not** performed by any script in this repository.

Decisions this follows: sprints/v3/PRD.md §5.8 and Decisions M (Neon PostgreSQL via the Vercel Marketplace, single administrator credential in environment variables), O (Vercel project to be confirmed), P (Neon point-in-time restore plus a weekly manual encrypted dump).

## 1. What gets deployed

| Piece | Where it runs | Source |
|---|---|---|
| Magazine pages, `/welcome/`, `/admin/` | Vercel static hosting | `npm run build` → `_site/` (Eleventy) |
| Registration gate | Vercel Routing Middleware (edge) | `middleware.ts` + `lib/gate.ts` |
| API | Vercel Functions (Node 22) | `api/**/*.ts` (Web `Request`/`Response` handlers) |
| Data | Neon PostgreSQL | `db/migrations/*.sql`, applied with `npm run db:migrate` |

`vercel.json` sets the build command, output directory, trailing slashes and the security headers. Nothing provider-specific lives in publication logic; the same handlers run locally under `npm run dev:app`.

## 2. Prerequisites (once, on the operator's machine)

- Node 22 LTS, `npm install` in `05_WEBSITE/`.
- Playwright browser for the QA suites: `npx playwright install chromium`.
- PostgreSQL 16 client tools for local tests (`pg_ctl`, `psql`); `npm run db:local:start` creates a loopback-only cluster in `.pgdata/` (git-ignored).
- Vercel CLI (`vercel login` — interactive, run it yourself).
- A copy of `.env.example` as `.env.local` for local work. Never commit `.env.local`; `npm run check:secrets` fails if any `.env*` other than `.env.example` is tracked.

## 3. Environment variables

Set these in Vercel → Project → Settings → Environment Variables, **separately for Preview and Production** (different values for each). Generate values locally; never paste them into a file in this repository.

| Name | Purpose | How to generate |
|---|---|---|
| `DATABASE_URL` | PostgreSQL connection string (TLS) | Injected by the Neon Marketplace integration; for Preview use a Neon branch |
| `SESSION_SECRET` | HMAC key for visitor cookies and CSRF tokens | `openssl rand -base64 32` |
| `IP_HASH_SALT` | Salt for IP hashing (rate limits, visit records) | `openssl rand -base64 24` |
| `ADMIN_USERNAME` | The single administrator's username (Decision N — supplied by the owner) | choose; ≤ 64 characters |
| `ADMIN_PASSWORD_HASH` | argon2id hash of the administrator password | `npm run admin:hash` (masked prompt; prints only the hash) |
| `REGISTRATION_ENABLED` | Emergency switch; `false` closes registration with a maintenance notice | `true` normally |
| `BATCH_YEAR_MIN` | Earliest accepted pass-out year (Decision J) | `1950` |
| `NODE_ENV` | `production` on Vercel (enables `Secure` cookies and HSTS) | set by Vercel |

Rotating `SESSION_SECRET` logs every visitor out (they simply register again) and invalidates every CSRF token; rotating `ADMIN_PASSWORD_HASH` changes the administrator password with no other effect.

## 4. First-time setup (preview environment)

1. In `05_WEBSITE/`: `vercel link` → create a **new** project (owner/team per Decision O). Framework preset: *Other*. Root directory: `05_WEBSITE`. The functions in `api/` export a Web-standard `fetch(request)` handler — Vercel's Node runtime treats a *default* export as the `(req, res)` signature and silently discards its `Response`.
2. Vercel → Storage / Marketplace → add **Neon** (PostgreSQL). Accept the integration so `DATABASE_URL` is injected for Preview and Production. In Neon, keep a `main` branch for production and use a **branch** for previews.
3. Create a least-privilege application role in Neon and use it in `DATABASE_URL`:
   ```sql
   create role becaa_app login password '<generated>';
   grant connect on database <db> to becaa_app;
   grant usage on schema public to becaa_app;
   grant select, insert, update, delete on all tables in schema public to becaa_app;
   grant usage, select on all sequences in schema public to becaa_app;
   ```
   Migrations run with the owner role (`npm run db:migrate` with the owner `DATABASE_URL` exported in your shell), the application role never has `CREATE`/`DROP`.
4. Set the variables from §3 for **Preview**.
5. Apply the schema to the preview branch: `DATABASE_URL='<preview owner url>' npm run db:migrate` then `npm run db:status` (expect `Applied: 1`).
6. `vercel deploy` → note the preview URL.
7. Verify the preview: `npm run e2e:app -- --base-url https://<preview>.vercel.app` with `E2E_ADMIN_USERNAME`/`E2E_ADMIN_PASSWORD` exported for that shell only (the same credential you hashed in step 4). Also open the preview on a phone: `/` must show the welcome page, registration must open the magazine, `/admin/` must require login.
   Previews are behind Vercel Deployment Protection. The suite authenticates with either the project's *Protection Bypass for Automation* secret (`VERCEL_AUTOMATION_BYPASS_SECRET`, sent as `x-vercel-protection-bypass`; `vercel curl` creates one on first use) or the local Trusted Sources token (`VERCEL_OIDC_TOKEN` from `vercel env pull`, sent as `x-vercel-trusted-oidc-idp-token`). Export either for that shell only; the suite never prints them. Registration is limited to 5 per 10 minutes per IP, so wait 10 minutes between remote runs.
8. Record the preview URL and commit in `sprints/v3/PREVIEW_DEPLOYMENT.md` (Task 35).

## 5. Production release (only after explicit approval)

1. Run the full release pipeline at the commit to be released: `npm run release:v3` (validation, unit/integration tests, build, site tests, visual QA, PDF, PDF QA, advertisement-background review, application E2E, secret and SQL gates, dependency audit) and complete `/walkthrough`.
2. Set the **Production** variables (§3) — fresh secrets, not the preview ones.
3. Apply the schema to the production database: `DATABASE_URL='<production owner url>' npm run db:migrate`.
4. Deploy exactly the reviewed commit: `vercel deploy --prod` (or promote the verified preview in the Vercel dashboard).
5. Post-deployment smoke test on desktop and mobile: `/` → welcome; register → magazine (cover, 44 items, Bengali text, tinted advertisement cards); direct image URL without cookie → 403; `/admin/` → login → dashboard → CSV; `/api/health` → `{"ok":true,"db":true}`.
6. Record deployment time, release ID (`V3_REVIEW_01`), commit and public URL in `CHANGELOG.md` and in `06_FINAL_OUTPUT/V3_REVIEW_01/DEPLOYMENT.md`.

## 6. Rollback

- **Site/functions:** Vercel → Deployments → previous production deployment → *Instant Rollback*. Keep the last known-good deployment available (Vercel retains it).
- **Database:** migrations are additive and forward-only; an older deployment keeps working against a newer schema. A destructive change is never shipped in the same release as the code that depends on it. Each migration has a reverse file: `npm run db:rollback -- <version>` runs `db/rollback/NNN_*.sql` and removes the ledger entry (destroys that migration's data — deliberate use only).
- **Data damage:** restore from Neon point-in-time recovery (Neon console → branch → *Restore*), or from the latest manual dump (§8).
- **Emergency close:** set `REGISTRATION_ENABLED=false` and redeploy (or change the variable and let Vercel re-run the functions); `/api/register` returns a 503 maintenance notice, existing visitor sessions keep working.

## 7. Retention and deletion (PRD §5.6, Decision L)

- Visitor records are retained until **31 December 2027**, then purged by the owner: `DATABASE_URL='<production url>' npm run db:purge` (also clears `visits.ip_hash` older than 30 days, stale `rate_limits` rows and expired admin sessions — safe to run at any time).
- Delete one visitor on request: from the dashboard (Delete button), or `npm run db:purge -- --email <address>`.
- No unattended cron job purges data in this sprint.

## 8. Backups (Decision P)

- Neon keeps point-in-time history for the retention window of your plan; check it in the Neon console after setup.
- Weekly manual dump, owner-held, encrypted:
  ```sh
  pg_dump "$DATABASE_URL" --no-owner --format=custom | gpg --symmetric --cipher-algo AES256 > becaa-visitors-$(date +%F).dump.gpg
  ```
  Store it outside the repository and outside any public location. Restore with `gpg --decrypt … | pg_restore --dbname "$DATABASE_URL" --clean --if-exists`.
- The administrator CSV export is **not** a backup (it omits internal fields).

## 9. Operations checklist

- `npm run check:secrets` and `npm run check:sql` before every commit that touches `api/`, `lib/` or docs.
- `npm audit`: new application dependencies must be clean; the four pre-existing build-tool advisories are tracked in the release allow-list (Task 36).
- Logs on Vercel contain method, path, status and one audit line per CSV export (timestamp, session display id, row count) — never bodies, cookies or emails.
- Rate limits: 5 registrations per 10 minutes per IP hash; 5 admin login attempts per 15 minutes per IP and lockout after 10 failures per username. Both self-expire.
